# Python UDF JIT 使用指南

面向试用和灰度验证人员的快速上手手册。你不需要了解编译原理、字节码或 Ray 内部细节——
本指南回答四个问题：**它能做什么、怎么安装、怎么启用、怎么验证结果**。

> **当前发布状态**：截至 2026-07-29，项目已通过单物理宿主三容器预发布验收，
> 但真实三物理节点门禁、Python 3.11.6 生产适配和首发业务绑定仍未完成。
> 当前机器可读状态为 `release_ready=false`，请勿将本指南视为生产发布承诺。

---

## 1. 这个工具是做什么的？（一句话版）

**它为 Daft/Ray 作业中符合条件的标量 Python 函数（UDF）提供透明的 CinderX JIT 加速路径。**

具体来说：当你在 Daft 里用 `where`、`select`、`with_columns` 写了 Python 自定义函数来处理数据时，
本工具会尝试捕获其中受支持的标量区域，并在工作进程中编译为本地机器码。你无需修改 UDF 源码或
Daft 调用方式，但仍需完成安装、环境锁定和灰度配置。

不符合支持矩阵的区域会保留 Python 解释执行路径。是否实际进入 JIT、是否获得收益，必须通过解释报告、
正确性对比和同环境 A/B 测量确认；**不是所有 UDF 都会被编译，也不保证每个负载都会变快**。

## 2. 当前能力和适用范围

| 能力 | 当前边界 |
|---|---|
| ✅ 透明接入 | 不修改 UDF 源码及 `where`、`select`、`with_columns` 的调用方式 |
| ✅ 标量执行路径 | 运行时具备 `bool`、`int32`、`int64`、`float32`、`float64` 五种标量槽位 |
| ✅ 正确性契约 | 已验证范围内，`off`、`observe`、`auto` 应保持结果、异常和行序语义一致 |
| ✅ 启动边界回退 | 新作业可改用 `off`，也可回滚到已批准的镜像和 Wheel |
| ⚠️ 性能未定级 | 当前只有方向性观测，可能变快、持平或变慢，不构成加速保证 |
| ⚠️ 尚未发布就绪 | 当前最高灰度状态为 `observe-ready`，不应直接用于生产 `auto` |

**哪些场景更可能进入当前 JIT 路径？**

- 单标量输入、单标量输出的纯数值计算；
- 受支持的加、减、乘运算；
- 数值比较和简单条件选择；
- 运行时布局属于 `bool`、`int32`、`int64`、`float32`、`float64` 之一。

五种标量槽位都已完成运行时与制品布局验证，但一个具体 Daft UDF 能否端到端进入 JIT，
还取决于数据模式、字节码、效应分析、守卫和冻结策略；应以该 UDF 的解释证据为准。

**哪些场景目前不会进入 JIT，或只有部分区域可能进入？**

- 字符串处理、文本操作
- 列表、字典、结构体和其他 Python 对象
- 多参数或复杂返回结构
- 取模、整除及其他未进入当前标量提供器支持集的运算
- I/O、不可控副作用和无法证明的非确定性调用
- 向量、Arrow 或列式批处理执行

> 在提交到优化区域之前发现不支持、守卫不匹配或编译失败时，系统会回到解释执行路径。
> UDF 本身原有的异常仍应按原语义传播；“可回退”不等于吞掉业务异常，也不等于没有额外开销。

## 3. 安装前的准备

当前候选使用锁定环境验证。阻断项不匹配时，不应进入 JIT 灰度：

| 检查项 | 要求 |
|---|---|
| Python | 当前开发验证版本为 **3.14.3**；生产目标 **3.11.6** 尚未完成适配和资格验证 |
| Daft | 阻断项，精确匹配 **0.7.2**，并通过私有 API/源码指纹检查 |
| Ray | 阻断项，精确匹配 **2.55.0** |
| PyArrow | 阻断项，精确匹配 **22.0.0** |
| Lance | 候选基线为 **7.0.0**；兼容性命令把它列为非阻断项，正式候选仍需固定指纹 |
| CinderX | 必须使用候选绑定的提交、补丁、Wheel 和 CPython SOABI；仅“已安装”并不足够 |

> `python-udf-jit` 的 Wheel 当前不声明或自动安装上述运行时依赖。请使用部署方提供的

## 4. 三步完成 `off` 模式验证

### 第 1 步：安装已批准的 Wheel

```bash
python -m pip install /绝对路径/python_udf_jit-0.1.0-py3-none-any.whl
```

当前文档没有证明该包已发布到公共 PyPI，因此不要把 `pip install python-udf-jit` 当成正式安装来源。
Wheel 文件名和版本以部署方交付的候选为准。

### 第 2 步：安装启动引导文件

安装完成后，必须执行一次引导安装，把随包附带的 `.pth` 文件放到 Python 的库目录：

```bash
python -m python_udf_jit.bootstrap_install --purelib /你的/python/purelib/绝对路径
```

> **怎么找当前解释器的 `purelib` 路径？**
>
> ```bash
> python -c 'import sysconfig; print(sysconfig.get_path("purelib"))'
> ```
>
> 目标目录必须由当前用户拥有、不是符号链接，且不能由组或其他用户写入。
> 安装器会以 `0644` 创建引导文件；重复执行仅在文件内容和权限完全一致时成功。

### 第 3 步：用 `off` 启动一个新作业

```bash
# 初始安全配置：启用插件入口，但不捕获、不编译、不执行优化代码
export UDFJIT_PLUGIN_ENABLE=1
export UDFJIT_MODE=off

python /绝对路径/your_daft_job.py
```

这一步用于确认安装引导不会改变原作业的结果、异常和行序。

> `observe` 和 `auto` 不是只改一个变量就能安全投入使用。非 `off` 模式还需要部署系统提供
> 锁定的兼容性清单（当前透明入口使用 `UDFJIT_MANIFEST_PATH`）、唯一的运行/集群身份、
> 冻结策略以及一致的驱动节点和工作节点镜像。不要自行伪造这些发布输入。

## 5. 三种模式，怎么选？

模式在新作业/新进程启动边界生效，可以理解成三个档位：

> **实现核对提示**：当前透明启动入口和 Worker 包装器仍直接读取 `UDFJIT_MODE`，
> `resolve_environment_mode` 尚未接入这条生产调用链。因此，本节描述的是发布治理契约，
> 不能视为 `UDFJIT_DISABLE`、插件开关、兼容性和策略授权均已端到端生效的证明。

```
  off（关闭）      →     observe（观察）     →     auto（自动加速）
  不捕获                 捕获，可选影子编译             允许优化执行
```

| 档位 | 会捕获你的函数吗？ | 会在后台编译吗？ | 会真的加速执行吗？ | 适合什么时候用 |
|---|:---:|:---:|:---:|---|
| **`off`** | 否 | 否 | 否 | 安装验证、正确性基线和回退 |
| **`observe`** | 是 | 仅当策略和作业同时允许影子编译 | 否 | 候选识别、解释信息和灰度观测 |
| **`auto`** | 是 | 是 | 仅在兼容且策略授权时 | 受控验收或已批准的灰度 |

### 为新作业选择请求模式

```bash
export UDFJIT_MODE=off        # 关闭
export UDFJIT_MODE=observe    # 观察
export UDFJIT_MODE=auto       # 自动加速
```

修改环境变量不会改变已经运行的作业或工作进程。

### 模式解析契约

1. **解析优先级**（从高到低）：

   ```
   UDFJIT_DISABLE → UDFJIT_PLUGIN_ENABLE → UDFJIT_MODE → 兼容性检查 → 策略
   ```

   低优先级输入只能收紧能力，不能扩大权限。

2. **本地停用不是运行中急停**：治理解析器把 `UDFJIT_DISABLE=1` 定义为新进程启动时的本地停用输入。
   本期没有运行中分布式紧急停用通道，也不会中断已经进入执行的区域。

3. **`auto` 需要独立授权**：请求 `auto` 不代表一定生效。兼容性、策略模式上限、
   标量提供器开关和 `rollout_authorized=true` 必须同时满足；未授权请求会收紧为 `observe`
   （模式决策原因码：`rollout_not_authorized`）。

4. **策略随作业冻结**：运行中的工作进程不会从远端拉取新策略，也没有“运行中开关”。

### 推荐的灰度（渐进上线）路径

```
  第 1 阶段：UDFJIT_MODE=off       建立正确性和性能基线
              ↓ 确认没问题
  第 2 阶段：UDFJIT_MODE=observe   查看捕获、校验和解释信息
              ↓ 看到函数被正确识别
  第 3 阶段：UDFJIT_MODE=auto      仅在发布前置条件完成并获授权后进行 A/B
```

当前候选的发布上限仍是 `observe-ready`；第 3 阶段只适用于受控验收环境，不是现阶段的生产建议。

## 6. 怎么确认它生效了？

`udfjitctl` 是本地只读检查工具。它读取已有的清单、制品或报告并输出 JSON；
它不会提交 Daft 作业，也不会自动生成解释报告或运行性能基准。输入文件通常由部署/验收流程导出。

### 6.1 检查环境兼容性（装对了没？）

使用部署方提供的私有兼容性清单：

```bash
udfjitctl compatibility --manifest /绝对路径/manifest.json
```

通过时的输出结构如下：

```json
{
  "manifest_sha256": "<64 位 SHA-256>",
  "mismatches": [],
  "reason_code": "compatible",
  "schema_version": 1,
  "status": "pass"
}
```

- `"status":"pass"`：Python、Daft、Ray、PyArrow 和 Daft API 通过该命令覆盖的阻断检查；
- `"status":"fail"`：`mismatches` 列出不匹配的组件或 `daft_api`。

`pass` 不等于完整发布资格：CinderX 指纹、镜像一致性、多节点证据和发布前置条件仍由正式验收流程检查。

### 6.2 检查一个已导出的制品

运行时制品通常内联在载体中或存放于 Ray `ObjectRef`，不一定形成普通用户可见的本地文件。
如果部署流程导出了制品，可以检查其严格格式和内容哈希：

```bash
# 严格解码并验证内容完整性
udfjitctl artifact verify /绝对路径/artifact.bin

# 查看格式、目标运行时、语义哈希、操作数和区域数
udfjitctl artifact inspect /绝对路径/artifact.bin
```

`verify` 证明文件满足制品格式和完整性约束，不单独证明它来自可信发布源。

### 6.3 读取解释报告（为什么进入或没有进入 JIT？）

```bash
udfjitctl explain /绝对路径/explain.json
```

该命令严格校验并规范化已有报告。报告阶段固定为：

```
adapter → capture → ir → artifact → layout → variant → execute
```

常见原因码包括：

- `candidate_discovered`：发现候选；
- `capture_succeeded` / `capture_rejected`：捕获成功/被拒绝；
- `artifact_verified` / `artifact_load_rejected`：制品验证通过/加载被拒绝；
- `compile_submitted` / `compile_failed`：已提交编译/编译失败；
- `variant_cache_hit`：命中已编译变体；
- `semantic_execute`：进入受控语义执行。

报告只包含有限枚举、计数和摘要，不包含业务值。模式解析原因（例如
`rollout_not_authorized`）与治理事件原因码属于不同输出面，不应假定一定出现在该解释文件中。

### 6.4 读取主线性能报告

```bash
udfjitctl benchmark mainline --config /绝对路径/profile.json
```

尽管子命令名为 `benchmark`，它**不会现场运行基准**。它只校验并摘要一个已有的主线性能
Profile，返回 `performance_status`、`speedup` 和 `conclusion_scope` 等字段。
`speedup` 定义为 `off 时间 / auto 时间`：大于 1 表示候选较快，小于 1 表示候选较慢。

方向性 A/B 应由验收流程在同一镜像、数据、机器和配置下分别启动新的 `off` 与获授权的 `auto`
作业，先验证正确性，再记录预热、多次交替和汇总结果。当前性能状态为 `unqualified`，
单次计时不能写成正式收益结论。

### 6.5 验证结果正确性

在受控 `auto` A/B 中，至少对比：

| 检查项 | 期望结果 |
|---|---|
| 作业状态和异常 | 成功/失败状态、异常类型与语义边界一致 |
| 数据模式和行数 | 完全一致 |
| 行序 | 当作业承诺顺序时完全一致 |
| 值语义 | 数值、空值、NaN 等按既定比较规则一致 |
| 正确性摘要 | 使用同一规范化算法计算，摘要一致 |

无序多重集哈希只适合顺序不构成契约的场景；它不能替代模式、行序、异常和边界值检查。
哈希一致是强证据，不是“任何输入都绝对正确”的证明。

## 7. 诊断命令一览表

所有命令都要求输入是当前用户拥有的普通文件，大小不超过 16 MiB，且组和其他用户没有任何权限；
符号链接会被拒绝。常用做法是把部署方提供的文件复制到私有目录后执行 `chmod 0600 <文件>`。

| 命令 | 作用 | 成功时退出码 |
|---|---|:---:|
| `udfjitctl compatibility --manifest <文件>` | 检查清单覆盖的阻断版本和 Daft API | 0 |
| `udfjitctl artifact verify <文件>` | 严格解码并验证制品完整性 | 0 |
| `udfjitctl artifact inspect <文件>` | 输出制品的结构化元数据 | 0 |
| `udfjitctl explain <文件>` | 校验并规范化已有解释报告 | 0 |
| `udfjitctl benchmark mainline --config <文件>` | 校验并摘要已有主线性能 Profile | 0 |

文件读取、格式校验或状态检查失败时退出码为 `2`，并输出包含 `reason_code` 的 JSON。
命令名或参数写错时由 `argparse` 直接报错，退出码同为 `2`，但输出不是上述 JSON 结构。

## 8. 想要安全地回退怎么办？

本期没有运行中分布式紧急停用通道。标准回退在新作业和部署边界完成：

```bash
# 在提交新作业前设置
export UDFJIT_MODE=off
```

`UDFJIT_DISABLE=1` 是治理契约中的新进程本地停用输入，不是运行中按钮。回退时应：

1. 停止提交新的 `auto` 作业。
2. 让已经进入执行的区域自然完成，不在区域中途替换模式或策略。
3. 以 `UDFJIT_MODE=off` 提交新作业，并重新执行正确性检查。
4. 如需部署回滚，重新部署已批准的镜像和 Wheel，并建立新的候选清单。
5. 替换旧工作进程，确认旧进程代际、变体和制品句柄不再存活。
6. 重跑兼容性、`off` 正确性和清理检查。

冻结策略包含硬性预算。当前默认值如下：

| 预算项 | 默认值 |
|---|---:|---|
| 单命名空间变体数 | 64 |
| 单命名空间代码字节数 | 64 MiB |
| 单进程命名空间数 | 32 |
| 单进程变体数 | 256 |
| 单进程代码字节数 | 256 MiB |
| 编译并发数 | 1 |
| 待编译队列长度 | 32 |
| 单次编译超时 | 30 秒 |
| 负缓存条目数 | 1024 |
| 负缓存有效期 | 30 秒 |
| 熔断失败阈值 | 3 |
| 熔断复位时间 | 30 秒 |

这些默认值用于限制编译和缓存影响。达到容量、超时或熔断条件时，系统会拒绝新的优化尝试；
在允许回退的提交前边界继续解释执行。它们不能保证“零开销”，实际冻结策略也可能进一步收紧预算。

## 10. 常见问题（FAQ）

**Q1：装了之后我的作业会变慢吗？**

有可能。`off` 不捕获、不编译，也不执行优化代码；启动引导仍会做一次轻量导入，因此不应写成严格
“零开销”。`observe` 和 `auto` 会增加捕获、校验或编译成本，不支持路径也可能有开销。
现有 FineWeb 200K 文本负载方向性记录中，`auto` 比 `off` 慢 2.64%；请以自己的同环境 A/B 为准。

**Q2：我怎么知道我的函数有没有被加速？**

查看部署流程导出的解释和验收证据。仅有 `candidate_discovered` 不代表已加速；应同时看到捕获/制品
通过、编译提交或变体命中，以及 `semantic_execute` 等执行证据。正式资格报告中的
`execution_mode=cinderx-jit` 比单条候选事件更有证明力。

**Q3：加速效果不稳定怎么办？**

当前性能状态是 `unqualified`。固定镜像、依赖、数据、机器和配置，完成预热后交替运行多次，
同时报告离散度和中位数；不要用一次运行或不同环境的计时下结论。

**Q4：支持我的字符串处理 UDF 吗？**

暂不支持 JIT。字符串、列表、字典等复杂类型不在当前优化范围；在满足提交前回退条件时继续走
原解释路径。原 UDF 的异常和副作用语义仍需按正常方式验证。

**Q5：报错说 `runtime_dependency_mismatch` 是什么意思？**

Python、Daft、Ray 或 PyArrow 与清单不一致，或者 Daft 私有 API 检查未通过。
查看输出中的 `mismatches`，再核对第 3 节。该错误不覆盖所有发布指纹检查。

**Q6：设了 `auto` 为什么没生效？**

可能原因包括策略未授权或模式上限较低、兼容性失败、提供器关闭、UDF 不在支持矩阵、
守卫不匹配、清单缺失或工作进程身份不完整。先用 `observe` 收集证据，再由部署负责人核对冻结策略；
普通用户不应自行把 `rollout_authorized` 改为 `true`。

## 11. 重要边界（使用前必读）

为了让你的预期和工具的实际能力对齐，请了解以下边界：

| 边界 | 说明 |
|---|---|
| 🔵 已实现并完成当前范围验证 | 五种标量布局、受支持的算术/比较/分支、透明接入、守卫和提交前回退 |
| 🟡 发布前仍需完成 | 真实多物理节点验证、Python 3.11.6 生产适配、首发业务与目标集群绑定 |
| 🔴 不支持 | 字符串/列表/结构体 JIT；向量/列式执行；跨节点机器码缓存；远程策略热更新 |

> **当前发布状态**：单物理宿主上的 Head/Driver 加两个 Worker 容器通过了全部已执行门禁，
> 但完整发布契约仍缺真实三物理节点证据，Python 3.11.6 生产资格和首发业务也未完成。
> 机器状态保持 `unit_completion_status=incomplete`、`release_ready=false`。
> 在这些前置条件完成前，不得表述为“功能完成”“发布就绪”或“性能已定级”。
